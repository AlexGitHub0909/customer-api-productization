# 项目发现与证据工作流

## 1. 建立项目拓扑

先识别仓库边界、运行单元和部署关系，再找文件。可使用 manifest、workspace、路由注册、构建配置、部署清单和进程入口确认真实结构。

记录：

- 工作区与仓库列表；
- 对外服务、管理后台、异步 worker、文档站和客户示例；
- 数据库、消息系统、对象存储和外部依赖；
- 本次可访问与不可访问部分；
- 生成物、归档和第三方代码等排除项。

## 2. 按能力建立证据链

每项拟开放能力都建立以下链路：

```text
客户目标
  -> 产品范围和规则
  -> 外部入口与机器契约
  -> 认证、授权和租户
  -> 业务编排与状态变化
  -> 数据和副作用
  -> 异步任务与外部依赖
  -> 测试和执行结果
  -> 接入及运维文档
```

缺少任一环节时标记 `PARTIAL`、`PLANNED`、`UNKNOWN` 或 `BLOCKED`，不要自动补推。

## 3. 事实优先级

同一问题存在冲突时，通常按以下顺序核实：

1. 当前运行实现和当前数据库约束；
2. 当前机器契约、路由和输入校验；
3. 当前可重复执行的测试结果；
4. 已批准的产品、权限和运营决定；
5. 接入指南、README、历史计划和示例。

代码只能证明“当前如何运行”，不能单独证明“产品应该如此”。产品意图与实现冲突时，记录差异并由责任人裁决。

## 4. 变更影响追踪

新增或修改字段、状态、动作、事件时，同时追踪：

- 机器契约和版本兼容；
- 运行序列化与校验；
- 沙箱与生产；
- 错误码与重试建议；
- Webhook、事件和异步任务；
- 示例、集合和 SDK；
- 负向、回归和契约测试；
- 监控、支持和变更记录。

只改接口描述而未核对这些消费者，不算完成产品化变更。

## 5. 新鲜证据

交付前重新运行与本次范围对应的最小检查集。记录命令、时间、目标版本、返回码和关键结果。旧测试只有在依赖的实现、契约、配置和生成物均未变化时才可复用，并需说明依据。

每次试点或 GA 判断还应记录：

- 本次覆盖的能力、版本和明确排除项；
- Git SHA、发布版本或其它可复现的源版本标识；
- 带时区的审查时间；
- 契约、运行时、示例、测试、安全和容量证据的实际观察时间；
- 工作区含未提交变更时的基线及脏工作区说明。

只引用“测试文件存在”或历史测试结论，不算当前执行证据。
