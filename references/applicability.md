# 适配性与成熟度门禁

## 判断原则

通用性不是让所有项目都进入同一套模板，而是让同一种高价值问题在不同技术栈和目录结构下得到稳定结果。客户 API 产品化只适用于需要跨组织、长期、可治理接入的业务能力。

## 三种适配结论

### `PRODUCTIZE`

同时满足：

- 明确的外部客户或合作伙伴系统；
- 两个以上可复用接入，或一个需要长期维护且业务关键的接入；
- 业务成功、失败、状态和数据所有权已基本稳定；
- 客户身份、租户和授权可被实现与验证；
- 可提供隔离沙箱，或同等安全的联调环境和测试账户；
- 有产品、工程、运营和支持责任人；
- 有权开放相关数据和动作。

允许部分能力仍处于试点，但必须能明确收窄范围和停止条件。

### `DISCOVERY_ONLY`

目标方向合理，但至少一项关键前提尚未确认，例如：

- 底层能力存在，客户边界或用例未定；
- 业务流程尚未稳定到可以承诺外部契约；
- 权限、合规、商业或上游授权等待确认；
- 暂无安全联调环境；
- 运维和支持责任尚未归属。

只输出当前事实、候选范围、风险、验证任务和升级到 `PRODUCTIZE` 的条件。

### `NOT_SUITABLE`

出现以下任一事实时通常不适合：

- 只有内部调用，没有外部客户产品目标；
- 明确是一次性、短期或人工可控的数据交换；
- 目标只是把内部或上游接口原样透传；
- 无法建立租户隔离或数据授权；
- 接口副作用无法与生产隔离；
- 没有长期维护和支持责任；
- 预期收益不足以承担版本、兼容、安全和支持成本。

建议改用内部 API 设计、集成适配器、批量导入导出、托管操作或一次性交付流程。

## 硬阻塞项

以下项目不能靠“先写文档”解决：

1. 不知道谁有权读取或执行某项业务；
2. 无法防止客户 A 访问客户 B 的数据；
3. 测试调用可能触发真实收费、通知、订单或上游写入；
4. 外部写操作结果未知时没有对账或人工收口机制；
5. 凭证只能明文长期保存或会进入日志；
6. 无人负责故障、客户支持、版本兼容和停用；
7. 底层业务在关键状态和收费口径上仍无确定答案。

## 试点与 GA 的区别

`PILOT_PACKAGE_READY` 可以限制客户、scope、流量、场景和支持时段，但安全、租户、数据边界、契约和故障收口不能降级。

`GA_PACKAGE_READY` 还需要：

- 至少一次受控端到端接入或等价的生产级演练证据；
- 清晰的兼容和废弃策略；
- 支持值班、告警和升级路径；
- 发布、回滚和停用演练；
- 客户通信和变更记录机制。

不要用打分平均掉硬阻塞项。安全和授权缺失时，即使其它条件很好，也不能判定就绪。
